> **凡是你自己项目里跑过一遍的，自然就记住了；凡是靠背的，面试官一句"那你项目里这个指标是多少"就露馅。**

## 2. 执行顺序（3~4 周排期）

**不要按 01→08 顺序读完再动手。** 正确节奏是「读一小块 → 立刻改造项目 → 卡住了再回来读」：

```text
Week 1  ─ 读 01 主干(1天) ──► M1 指标定义 ──► M2 Golden Dataset + 首版基线
                                                      │
Week 2  ─ 读 02 主干(0.5天) ─►（同上收尾）──► 读 03 主干(0.5天) ──► M3 全链路观测
                                                      │
Week 3  ─ 读 05 §三/四/五/七(0.5天) ──► M4 安全评测 ──► 读 06 主干(0.5天) ──► M5 指标与告警
                                                      │
Week 4  ─ 读 07 §二/§四(0.5天) ──► M6 生产化与 CI ──► M7 报告与 README 指标
                                                      │
                                        收尾：补 04 的 trace_id 关联、复盘卡住的点
```

**依赖关系**（来自 08 篇 §5.0）：`M1 → M2 → M3 → M4 → M5 → M6 → M7`，其中 M3 可与 M2 并行，但 **M3 是 M4 的前置**（安全失败要能看 trace 才定位得了）。

**时间盒纪律**：04 和 06 是最容易失控的两篇（一个概念多、一个配置多）。各给自己 **1 天**，到点就跑通最小版本，别追求配置完整。

## 4. 必背清单（真的只有这些）

### A. 面试话术 · 能用自己的话讲，共 12 条

1. **调试 ≠ 评测**：改 prompt 改好 A 弄坏 B，结构原因是**无局部性 + 误差累积 + 非确定性**
2. **三层评测**：单元 / 组件 / 端到端；Agent 呈**沙漏形**，中腰在组件层，腰不细则端到端失败无法归因
3. **Agent 评测三难点**：多步（写轨迹断言）、工具副作用（假工具 + 录制回放）、非确定路径（跑 N≥3 报 `pass@N`）
4. **四类评测**：离线（回归门禁）/ 在线（发现新失败模式）/ 影子（双跑预演、成本翻倍）/ 金丝雀（小比例放量）
5. **回归测试 = 离线评测集接进 CI**，通过率下降即阻断合并
6. **门禁必须有 `hard_fail` 一票否决**，只比全局平均通过率的话，安全用例基本等于没测
7. **Task Completion Rate 是北极星**；Correctness 对参考答案、Faithfulness 对上下文、Context Recall 对检索
8. **Tool Call Accuracy 分选择级与参数级**；参数用 `args_contains` **子集匹配**而非全等，且"只查工具名不查参数"会漏掉危险写操作
9. **延迟看 P95/P99 不看均值**；**"结果正确但多做了未授权写操作"应判任务失败**
10. **judge 三种偏差**（位置 / 冗长 / 自偏好）+ 必须用人工标注校准，**同一模型不能既当选手又当裁判**
11. **拦截率与误拒率成对读**——单看任一个都会被骗
12. **Trace / Metrics / Logs 分工**：告警不能靠翻 trace；`user_id` 不能做 metric label（基数爆炸）

### B. 工程纪律 · 做的时候必须遵守，共 8 条

1. 评测用例含注入/越权 → **必须隔离环境 + 假工具**，否则会真的改生产
2. **单次运行不下结论**，N≥3 并标注 `pass@N`
3. **用例不能泄漏进 prompt**
4. **指标口径写死在 `METRICS.md`**：分子分母、统计粒度（用例级 vs 请求级）、重试只算一次调用
5. 每个指标都必须能回答「**出了什么问题、该改哪里**」，否则删掉
6. **告警必须实际触发过**，否则等于没配
7. **数字必须实测**——"基线难看不是问题，编数字才是"
8. 只修「评测暴露出来的缺陷」，**不重写业务逻辑**

## 5. 面试 12 问 · 答法要点

| 问题 | 答法骨架 | 出处 |
| --- | --- | --- |
| 你怎么知道改了 prompt 之后变好了？ | 离线评测集 + 基线快照对比 + 分类型门禁，不是"看着更好了" | 01 §3.3 / §8.4 |
| 你的 Agent 成功率多少？口径是什么？ | Task Completion Rate 的定义 + n + 环境 + 基线；主动说口径比数字重要 | 02 §4.4 / §5.1 |
| 检索效果怎么衡量？ | Context Recall / Context Precision + Hit Rate@K；**Precision 要加权因为要看排序** | 02 §3.2 / §3.3 |
| 幻觉怎么测？ | Faithfulness + 声明-证据对齐（矛盾率单列、要求为 0）+ 无答案用例 + 引用溯源校验 | 05 §二 |
| 怎么防 Prompt Injection？ | 直接/间接注入分类、间接入口清单、工具白名单、输出过滤、10 条红队用例进门禁 | 05 §3.1~3.4 |
| 成本怎么控？ | Token 口径 → Cost per Task → 五级降级阶梯 + 缓存 + 模型路由 | 02 §5.2/5.3 + 07 §6.1 |
| 线上出问题怎么排障？ | 分层排障：先看哪一层 → trace 的 span 逐层下钻 → `trace_id` 关联日志 | 03 §7.3 + 04 §7.3 |
| 怎么发布新版本？ | 三类变更（代码/prompt/模型）回滚粒度不同；影子→金丝雀→放量；发布前必跑评测集 | 07 §5 |
| 评测集怎么建？ | 九大类别 + 40/30/15/15 配比 + 失败用例回灌闭环（发现→去敏→写期望→先红→修复→转绿） | 01 §5 / §7.4 |
| 评测太慢太贵怎么办？ | 三层切分：本地快集 20 / PR 门禁 20 / 发版全量 100；judge 只抽查 ≤40 条 | 08 §8.2 |
| 非确定性怎么处理？ | `pass@N` + 调温度 + 收敛 prompt；报告里标注 n | 01 §2.4 |
| SLO 怎么定？ | SLI→SLO；线上 SLO 与离线评测**口径必须一致**，不一致时按维度缩小排查范围 | 06 §8.1 / §8.3 |

## 7. 验收：什么算"学完阶段 5"

### 三条硬标准

1. 我能打开 Langfuse / Grafana，**指着一个失败的 trace 讲清它错在哪一步**；
2. 我能报出 3~5 个**实测**数字，并说清**口径、样本量 n、对比基线**；
3. 我能讲一个完整故事：**"某次改 prompt 后某个类别掉了 1 条 → 门禁阻断合并 → 定位到工具白名单被绕过 → 修复后回归转绿"**。
