# 工具调用工程化：参数校验、超时、重试、降级与审计

> **定位说明**：本篇是阶段 3「Tools 与 MCP」的第二篇学习文档。上一篇你学会了如何定义工具、如何让模型发起并处理工具调用；本篇解决的是「工具调用在真实业务中如何稳定工作」。

## 一、为什么需要工具工程化

### 1.1 模型是不确定的调用方

模型生成工具调用参数的过程是概率性的：同一个问题，它可能给出合法参数，也可能给出越界数字、拼错的字段名、超长的字符串，甚至凭空捏造不存在的工具名。模型的「工具调用协议」本身也可能出错——参数缺失、格式不是合法 JSON。更麻烦的是，**模型不会主动承认自己错了**：如果你把一段内部堆栈抛给它，它很可能顺着错误信息编造一个「看起来合理」的修复，而不是如实告诉用户「系统暂时不可用」。

### 1.2 工具背后是真实的业务系统

工具一旦被调用，就会真实地读库、写库、调外部 API。失败的影响是真实的：订单查不到、库存扣多了、第三方接口被打爆。所以工具调用必须满足三个「必须」：

- **对用户可解释**：失败时用户得到的是「订单查询失败，请稍后重试」，而不是「java.sql.SQLException: Connection refused」；
- **对系统可恢复**：网络抖动时自动重试，依赖挂掉时走降级路径，而不是让异常一路炸穿 Agent 主流程；
- **对账可审计**：每一次工具调用（谁在什么时候调了什么工具、传了什么参数、结果如何、花了多久）都要留下记录，出了问题能追溯。

### 1.3 Java 类比：网关层的统一处理

如果你在 Java 后端做过微服务，你一定熟悉这个画面：网关或 BFF 层统一做「鉴权 → 参数校验 → 限流 → 熔断 → 日志」，业务 Service 只管业务。工具执行器（ToolExecutor）就是 Agent 世界的「网关」：

| Java 网关能力 | Agent 工具执行器对应能力 |
| --- | --- |
| 参数校验（Bean Validation） | Pydantic v2 参数模型 |
| HttpClient 超时 | `asyncio.timeout` + httpx timeout |
| Resilience4j / Sentinel 熔断限流 | 熔断器 + 令牌桶 |
| 重试（Spring Retry） | 指数退避重试封装 |
| AOP 日志切面 | 结构化审计日志 |

记住这个类比，本篇所有内容都能对上号。

### 1.4 工程化的边界：别为玩具项目造网关

执行器不是越多越好。一个只有两个工具、仅供本机调试的脚本，直接 `try/except` 就够了；当你出现以下信号时再上执行器：工具数量超过 5 个、有外部依赖（HTTP/DB）、会被多个 Agent 或服务复用、需要向业务方交代调用记录。判断标准很简单：**故障成本是否超过工程成本**——工具失败一次会造成用户投诉或资损，就值得为它建网关。

## 二、参数校验：不能只信模型

### 2.1 为什么

工具参数直接对接业务系统：`user_id = -1` 让查询语义错误，`limit = 1000000` 可能拖垮数据库，10 万字符的 `keyword` 可能打爆下游接口。校验不是「对模型不信任」，而是**把协议边界明确下来**——这也是给模型写的「使用说明书」的一部分。

### 2.2 用 Pydantic v2 建模（以你锁定的依赖版本文档为准）

Pydantic v2 中 `Field` 约束与 `model_validate` / `model_validate_json` 是主力 API（0.3.x 时代的 `parse_obj` 已废弃，不要用）：

```python
from typing import Literal
from pydantic import BaseModel, Field, ConfigDict, ValidationError

OrderStatus = Literal["CREATED", "PAID", "SHIPPED", "CANCELLED"]


class OrderQueryParams(BaseModel):
    """把业务规则写在类型里"""
    model_config = ConfigDict(extra="forbid")  # 拒绝未知字段，防止模型乱传参

    user_id: int = Field(gt=0, description="用户ID，必须为正整数")
    status: OrderStatus | None = Field(default=None, description="订单状态筛选")
    limit: int = Field(default=20, ge=1, le=100, description="返回条数，1~100")
    keyword: str | None = Field(default=None, max_length=50, description="关键词，最长 50 字符")


# 模型传参通常是 dict，直接校验
try:
    params = OrderQueryParams.model_validate(raw_args)
except ValidationError as exc:
    errors = [{"field": ".".join(map(str, err["loc"])), "message": err["msg"]}
              for err in exc.errors()]
    result = {"error": "参数校验失败", "errors": errors,
              "hint": "请根据 errors 修正参数后重新调用本工具"}  # 见第七节错误策略
else:
    result = await order_service.query(params)  # 校验通过才碰业务
```

如果上游传的是 JSON 字符串，用 `model_validate_json`；它内部会先解析 JSON，非法 JSON 同样抛 `ValidationError`，一套 `except` 逻辑就能覆盖「连 JSON 都解析不了」的情况。

校验失败的真正价值在于**让模型自纠错**：模型看到 `{"error": "参数校验失败", "errors": [{"field": "user_id", "message": "Input should be greater than 0"}], "hint": "..."}` 后，会重新生成参数再调一次。所以错误信息必须做到「机器可读 + 可行动」：`field` 要和参数模型字段一致，`hint` 要告诉模型怎么改。如果错误信息含糊（比如只返回「参数错误」），模型就只能瞎猜，形成多次无效调用——这也是后面要审计的原因。

### 2.3 业务校验：类型之外还要校验语义

`Field` 约束解决「形状」问题，业务语义（日期格式、sku 前缀、跨字段关系）需要额外校验。原则：**能写进类型就写进类型**——枚举用 `Literal`/`Enum`，日期用 `datetime`，正则用 `pattern`，模型也能从 schema 里学到；跨字段约束用 `@model_validator(mode="after")`，例如「开始时间必须早于结束时间」：

```python
@model_validator(mode="after")
def check_range(self):
    if self.start >= self.end:
        raise ValueError("start 必须早于 end")
    return self
```

### 2.4 输入大小限制：防止「胖参数」

除了 `max_length`，还要限制**参数整体大小**：把 `raw_args` 序列化后限制总字节数（例如 8 KB），超限直接拒绝并提示模型精简。这是防住模型把整篇文档塞进参数的最有效手段。

### 2.5 踩坑点

- **只校验类型不校验范围**：`int` 挡得住字符串，挡不住 `-1` 和 `10**9`，范围约束必须显式写；
- **默认忽略未知字段**：Pydantic v2 默认 `extra="ignore"`，模型多传的字段会被悄悄丢弃——业务上宁可 `extra="forbid"` 明确报错；
- **错误信息写给模型看，不是写给自己看**：错误里要带 `hint`（怎么修），模型才能完成「修正后重试」的循环，否则它会反复用同样的错参数调用；
- **校验失败也算一次工具调用**：要记审计（见第六节），否则你发现不了「模型反复传错参」这个质量信号。

## 三、超时控制

### 3.1 为什么

LLM 工具调用链路上有三处可能「卡死」：工具内部逻辑、模型自身的 Agent 循环、工具调用的下游 HTTP 服务。任何一处不设超时，用户的请求就可能挂几分钟，同时占着连接、占着算力。超时是成本控制的第一道闸。

### 3.2 单工具超时：`asyncio.timeout`（Python 3.11+）

Python 3.11 引入的 `asyncio.timeout` 是首选（更老的 `asyncio.wait_for` 也能用，但它创建的 Task 超时后可能仍在后台运行，需额外 `shield` 管理）：

```python
import asyncio


async def run_with_timeout(coro, timeout_seconds: float) -> dict:
    """执行一个工具协程，超时返回结构化错误（而非抛异常炸穿调用方）"""
    try:
        async with asyncio.timeout(timeout_seconds):
            return await coro
    except TimeoutError:
        return {"error": "timeout",
                "message": f"工具执行超过 {timeout_seconds}s，请缩小查询范围后重试"}
```

超时按工具分级配置，不要一刀切：内部查询 3~5s、写操作（涉及事务）10s、外部 ERP 15s。**整体 Agent 调用也要包一层总超时**——单工具超时只能保证「单个工具不卡死」，模型仍可能陷入「调用失败 → 重试 → 再失败」的死循环，所以用 `asyncio.timeout(30)` 包住 `agent.ainvoke(...)`，超时返回兜底话术「我处理超时了，请缩小问题范围或稍后重试」。总超时取「工具超时 × 模型最大工具轮数」的合理上界（如 6 轮 × 5s ≈ 30s），否则模型还没完成就整体超时，体验更差。

超时还直接关联成本：每次工具调用都消耗下游资源和模型推理 token，卡死的调用比失败的更贵——失败能立刻释放资源进入重试/降级，卡死则一直占着连接。给每次对话设定总超时上限，本质就是给成本设上限。

### 3.3 HTTP 下游超时：httpx

工具内部调外部服务时用 httpx 自带超时，可分别设置连接、读、写、连接池获取的超时（以你锁定的依赖版本文档为准）：

```python
import httpx

async with httpx.AsyncClient(
    timeout=httpx.Timeout(10.0, connect=3.0, read=8.0, write=8.0, pool=3.0)
) as client:
    resp = await client.get("https://erp.example.com/api/stock", params={"sku": sku})
    resp.raise_for_status()
```

### 3.4 踩坑点

- **不设超时**：任何 `await` 都可能是无底洞，`asyncio.timeout` 是最便宜的保险；
- **超时取消要记得清理**：`asyncio.timeout` 超时会取消当前任务，工具里开的数据库连接、临时文件要在 `finally` 里关闭，否则连接泄漏；
- **把超时错误直接抛给模型**：超时是暂时性错误，应转成结构化错误信息让模型「换一种方式问」或「如实告诉用户」，而不是让整个 Agent 崩溃。

## 四、重试：给暂时性错误第二次机会

### 4.1 哪些错误可重试

| 可重试（暂时性） | 不可重试（永久性） |
| --- | --- |
| 网络抖动、连接超时 | 参数校验失败（400 类） |
| 下游 5xx、网关 502/503 | 业务拒绝（如余额不足） |
| 429 限流（遵循 Retry-After） | 鉴权失败（401/403） |
| 数据库连接池暂时打满 | 工具不存在/方法不存在 |

实现上把异常分成 `RetryableError` 与 `NonRetryableError` 两个分支，**只对前者重试**。`TimeoutError` 要分情况：发生在「请求还没发出」阶段可重试；发生在「响应可能已到达」阶段（如下单）不能盲目重试。

### 4.2 幂等性判断：写操作重试要小心

查询天然幂等，重试一万次结果都一样；但**写操作（下单、扣款、发货）重试必须小心**——第一次请求可能已经成功只是响应丢了，重试就会重复执行。两种解法：**能设计成幂等就设计成幂等**（调用方生成幂等键 idempotency key，下游据此去重）；**不能保证幂等就不自动重试**（返回「业务已受理，请稍后查询确认」让用户决定）。

### 4.3 指数退避 + 抖动

「失败后立即重试」在并发下会形成惊群效应（所有请求同时打向刚恢复的服务）。标准做法是指数退避 + 随机抖动：

```python
import asyncio
import random


class RetryableError(Exception):
    """暂时性错误：网络抖动、5xx、429"""


class NonRetryableError(Exception):
    """永久性错误：参数错误、业务拒绝"""


async def retry_async(coro_factory, *, max_retries: int = 3,
                      base_delay: float = 0.5, max_delay: float = 8.0,
                      retryable: type[Exception] = RetryableError):
    """指数退避 + 抖动。coro_factory 每次返回一个新协程。"""
    for attempt in range(max_retries + 1):
        try:
            return await coro_factory()
        except retryable as exc:
            if attempt == max_retries:
                raise  # 重试耗尽：抛原始异常，保留根因，交给上层降级
            delay = min(max_delay, base_delay * (2 ** attempt))
            delay *= 1 + random.uniform(0, 0.3)  # 抖动 ±30%
            await asyncio.sleep(delay)
    raise RuntimeError("unreachable")  # 仅为类型提示
```

用法：`result = await retry_async(lambda: client.get(url), max_retries=3)`。若下游返回了 `Retry-After` 头，优先遵循它而不是自己的退避公式。

重试参数应该**按工具配置化**（每类工具独立的 `max_retries`、`base_delay`），而不是全局写死：查询类可以多试几次，写操作干脆 `max_retries=0`。同时把重试次数写进审计日志（见第六节 `retries` 字段）——如果某工具的重试率长期偏高，说明它的稳定性有问题，该修的不是重试策略而是工具本身。

### 4.4 踩坑点

- **无差别重试所有错误**：对永久性错误重试只会放大故障（参数错的重试一百次还是错）；
- **退避不加抖动**：N 个并发请求同时退避 2s/4s/8s，恢复瞬间还是会同时打进来；
- **重试耗尽后吞掉根因**：必须 `raise` 保留原始异常链，否则审计日志里只剩「重试失败」四个字；
- **重试要计入整体超时**：3 次重试 × 每次 5s，单工具实际最长可能 15s+，配工具超时和 Agent 总超时时都要算上。

## 五、降级与熔断：服务挂掉时的体面

### 5.1 降级（Fallback）

降级 = 主路径失败时走备选路径：主库查询失败 → 查只读副本/缓存；实时库存接口失败 → 返回缓存库存并标注「可能有延迟」；AI 摘要失败 → 直接返回原文。降级不是「假装成功」，而是**用降低新鲜度/精度的代价换取可用性**，并且要把事实告诉模型——返回给模型的降级说明要显式标注数据新鲜度，例如：`{"error": "degraded", "data": {"sku": "SKU-1001", "stock": 12}, "note": "实时库存服务暂不可用，以上为缓存数据（最多滞后 5 分钟），请告知用户"}`。这样模型既拿到可用结果，又不会把陈旧数据当成实时数据承诺给用户。

### 5.2 熔断：防止把故障打得更痛

依赖连续失败时，继续重试只会浪费资源、加剧下游压力。熔断器三态：**CLOSED** 正常放行 → 连续失败达阈值后 **OPEN**，直接短路走降级 → 打开期结束自动 **HALF_OPEN**，放行探针请求，成功则关闭、失败则重新打开。最小实现（生产级建议用现成库如 `aiobreaker` 或基于 Redis 的分布式熔断）：

```python
import time


class CircuitBreaker:
    """连续失败 failure_threshold 次后打开 open_seconds 秒；到期自动半开。"""

    def __init__(self, failure_threshold: int = 5, open_seconds: float = 30.0):
        self.failure_threshold, self.open_seconds = failure_threshold, open_seconds
        self._failures, self._opened_at = 0, None

    @property
    def is_open(self):
        return self._opened_at is not None and \
            time.monotonic() - self._opened_at < self.open_seconds

    def on_success(self):
        self._failures, self._opened_at = 0, None

    def on_failure(self):
        if self._opened_at is not None:
            return  # 半开探针失败：保持打开（重新计时）
        self._failures += 1
        if self._failures >= self.failure_threshold:
            self._opened_at = time.monotonic()


breaker = CircuitBreaker()


async def guarded_call(coro_factory, fallback):
    if breaker.is_open:
        return await fallback()  # 短路：不打下游，直接降级
    try:
        result = await coro_factory()
    except RetryableError:
        breaker.on_failure()
        raise
    else:
        breaker.on_success()
        return result
```

注意：`_failures` 计数在并发下不是协程安全的，生产环境要加锁或用原子操作——正如你在 Java 里给计数加锁一样。

还要分清熔断与重试的分工：**重试解决单次调用的暂时性抖动，熔断解决依赖的整体性故障**。两者配合的典型顺序是「限流 → 重试（有限次）→ 熔断 → 降级」：先让重试吸收抖动，连续失败超过阈值后熔断器打开，后续请求直接短路走降级，不再浪费重试。

### 5.3 限流：别让模型帮你把下游打爆

一个用户的对话可能触发几十次工具调用，多用户并发时下游可能被瞬间打爆。简单令牌桶：

```python
class TokenBucket:
    def __init__(self, rate: float, capacity: int):
        self.rate, self.capacity = rate, capacity
        self.tokens, self._last = capacity, time.monotonic()

    async def acquire(self) -> bool:
        now = time.monotonic()
        self.tokens = min(self.capacity, self.tokens + (now - self._last) * self.rate)
        self._last = now
        if self.tokens >= 1:
            self.tokens -= 1
            return True
        return False
```

限流失败时给模型的错误要可行动：「工具调用过于频繁，请稍等几秒再试」。生产环境优先用现成方案（Redis 分布式限流、网关层限流），自己写的桶只适合单机原型。

### 5.4 踩坑点

- **降级结果不标注**：模型把缓存数据当实时数据告诉用户，是最坑的「看似成功」；
- **熔断状态不共享**：多进程部署时每个进程一个熔断器，阈值被稀释，需要集中式方案；
- **降级也要审计**：标注 `degraded: true`，否则事后分不清「返回的是真数据还是兜底数据」。

## 六、审计日志：每一次调用都有据可查

### 6.1 为什么

工具调用是 Agent 与业务系统之间的「资金/数据通道」。出了问题要能回答：谁调的、传了什么、结果如何。没有审计，就只能靠用户投诉倒查。

### 6.2 结构化字段与 JSON Lines

用 `logging` + 每行一条 JSON（JSON Lines，方便 grep/管道进 ELK）。字段：`timestamp`、`trace_id`（贯穿一次用户请求）、`conversation_id`（贯穿一次对话）、`tool_name`、`args`（脱敏后）、`result_status`（ok/error/timeout/degraded）、`error_code`、`latency_ms`（含重试）、`retries`、`caller`：

```python
import json
import logging
import time

audit_logger = logging.getLogger("tool.audit")  # 单独 logger，便于按名过滤

entry = {"timestamp": time.strftime("%Y-%m-%dT%H:%M:%S%z"),
         "trace_id": ctx.trace_id, "conversation_id": ctx.conversation_id,
         "tool_name": "query_order", "args": masked_args,  # 脱敏后参数
         "result_status": "ok",      # ok | error | timeout | degraded
         "error_code": None, "latency_ms": 123, "retries": 1, "caller": "agent:main"}


def write_audit_log(entry: dict) -> None:
    audit_logger.info(json.dumps(entry, ensure_ascii=False, default=str))
```

用 `FileHandler` 追加写文件并设置 `Formatter("%(message)s")` 只留 JSON 本体。注意**失败/超时/降级路径同样要审计**——它们才是排查重点。

审计是监控的数据底座：错误率、`error_code` 分布、P95 延迟、重试率、降级次数这些指标都从审计日志聚合而来。建议先有审计、再做监控面板——连日志都没有就谈告警，等于盲人摸象。字段设计时多想一步「这个字段将来要支撑什么查询」，比如按 `tool_name + result_status` 分组、按 `latency_ms` 分桶。

### 6.3 脱敏：参数不能原样进日志

手机号、身份证、密码、Token 必须打码：

```python
import re


def mask_sensitive(v: str) -> str:
    v = re.sub(r"1[3-9]\d{9}",
               lambda m: m.group(0)[:3] + "****" + m.group(0)[-4:], v)          # 手机号
    v = re.sub(r"\d{17}[\dXx]",
               lambda m: m.group(0)[:6] + "********" + m.group(0)[-4:], v)      # 身份证
    v = re.sub(r"(?i)(password|token|secret)([\"']?\s*[:=]\s*[\"'])[^\"']+",
               r"\1\2***", v)                                                   # 键值对
    return v


def mask_args(raw: dict) -> dict:
    return {k: mask_sensitive(str(v)) if isinstance(v, str) else v
            for k, v in raw.items()}
```

更稳妥的做法：敏感字段（`password`、`id_card`）在参数模型里直接标记，序列化前整字段置 `***`，而不是依赖正则猜测。

### 6.4 Java 类比：AOP 日志切面

这就像 Spring 里的 `@Around("@annotation(LogAudit)")` 切面：方法进出时统一记录参数、返回、耗时。Python 没有注解切面，但**执行器/装饰器**就是等价物——ToolExecutor 的 `execute` 入口天然是一个切面点，日志逻辑集中一处，业务工具函数里不出现任何日志代码。

### 6.5 踩坑点

- **用 `print` 打日志**：无法分级、无法按名过滤、无法进日志管道；
- **把原始参数写进日志**：脱敏必须在写入前做；
- **trace_id 断链**：一次请求经过 Agent → 工具 → 下游，trace_id 要手动透传（LangChain 1.x 可在 `RunnableConfig`/回调里取，以你锁定的依赖版本文档为准）。

## 七、错误信息策略：三层错误，绝不混用

### 7.1 三层错误

| 层 | 接收方 | 内容 | 示例 |
| --- | --- | --- | --- |
| 第一层 | 模型（工具返回值） | 机器可读、可行动 | `{"error": "validation_error", "errors": [...], "hint": "..."}` |
| 第二层 | 用户（最终回答） | 人性化、无技术细节 | 「订单查询失败，请稍后重试」 |
| 第三层 | 日志/监控（内部） | 完整堆栈、根因、上下文 | `traceback.format_exc()` 全量入日志 |

同一个失败在三层的表达完全不同。以「下游 ERP 服务 5xx」为例：第一层给模型 `{"error": "downstream_error", "message": "库存服务暂时不可用", "hint": "可以稍后重试或改查缓存数据"}`；第二层给用户「库存信息暂时获取失败，请稍后重试」；第三层进日志的是 `HTTP 502 from erp-gateway, retried 3 times, trace: ...` 的完整堆栈。三层之间只通过 `error_code` 关联，互不泄漏。

### 7.2 为什么绝不能把内部细节给模型

工具返回内容会进入模型上下文。若包含数据库连接串、内部 IP、堆栈路径：**一是信息泄露**（可能被模型原样复述给用户，甚至被提示注入利用）；**二是误导模型**（模型会顺着错误细节「编造修复方案」，而不是如实反馈）；**三是审计污染**（同样的错误反复占用上下文、浪费 token）。给模型的错误信息永远只含：错误码、一句话说明、可执行的修正提示。

### 7.3 错误分类枚举

错误码枚举化，监控和告警才能聚合：

```python
from enum import Enum


class ToolErrorCode(str, Enum):
    VALIDATION_ERROR = "validation_error"    # 参数校验失败（不可重试）
    NOT_FOUND = "not_found"                  # 业务数据不存在
    TIMEOUT = "timeout"                      # 超时（视阶段可重试）
    RETRY_EXHAUSTED = "retry_exhausted"      # 重试耗尽
    CIRCUIT_OPEN = "circuit_open"            # 熔断打开
    RATE_LIMITED = "rate_limited"            # 限流
    DOWNSTREAM_ERROR = "downstream_error"    # 下游服务错误
    BUSINESS_REJECTED = "business_rejected"  # 业务拒绝（不可重试）
    UNKNOWN = "unknown"                      # 兜底
```

映射规则：`ValidationError → VALIDATION_ERROR`；`TimeoutError → TIMEOUT`；可重试异常重试耗尽 → `RETRY_EXHAUSTED`；`NonRetryableError → BUSINESS_REJECTED`；其他 → `UNKNOWN` 且必须打全量堆栈到第三层。

### 7.4 踩坑点

- **把 `str(e)` 直接塞给模型**：`str(e)` 往往含类名和内部信息，要显式构造错误消息；
- **错误码用自由字符串**：`"query failed"` 和 `"query_failed"` 无法聚合，必须枚举；
- **第一层错误里写中文长句**：模型解析 JSON 比解析散文可靠，结构化优先。

## 八、综合示例：一个完整的 ToolExecutor

把前七节串起来：带「校验 → 权限 → 超时 → 重试 → 降级 → 审计」的异步工具执行器，注册订单查询、库存查询两个工具。

```python
import asyncio, json, logging, random, time
from enum import Enum
from typing import Awaitable, Callable

from pydantic import BaseModel, Field, ValidationError

audit_logger = logging.getLogger("tool.audit")


class ToolErrorCode(str, Enum):  # 错误码枚举
    VALIDATION_ERROR = "validation_error"
    TIMEOUT = "timeout"
    RETRY_EXHAUSTED = "retry_exhausted"
    DOWNSTREAM_ERROR = "downstream_error"
    BUSINESS_REJECTED = "business_rejected"
    UNKNOWN = "unknown"


class RetryableError(Exception):
    pass


class NonRetryableError(Exception):
    pass


class OrderQueryParams(BaseModel):  # 参数模型
    user_id: int = Field(gt=0)
    limit: int = Field(default=20, ge=1, le=100)


class StockQueryParams(BaseModel):
    sku: str = Field(min_length=1, max_length=32, pattern=r"^[A-Z0-9\-]+$")


async def query_order(params: OrderQueryParams) -> dict:  # 纯业务
    if params.user_id % 3 == 0:  # 模拟连接池打满（可重试）
        raise RetryableError("db pool exhausted")
    return {"order_id": 10001, "user_id": params.user_id, "status": "PAID"}


async def query_stock(params: StockQueryParams) -> dict:
    if params.sku == "SKU-DOWN":
        raise RetryableError("erp 5xx")
    return {"sku": params.sku, "stock": 12}


async def query_stock_fallback(params: StockQueryParams) -> dict:  # 降级
    return {"sku": params.sku, "stock": 12, "cached": True, "lag_minutes": 5}


async def retry_async(coro_factory, *, max_retries=3, base_delay=0.3, max_delay=4.0):
    for attempt in range(max_retries + 1):
        try:
            return await coro_factory()
        except RetryableError as exc:
            if attempt == max_retries:
                raise
            delay = min(max_delay, base_delay * (2 ** attempt)) * (1 + random.uniform(0, 0.3))
            await asyncio.sleep(delay)
    raise RuntimeError("unreachable")


class ToolExecutor:  # 工程化网关
    def __init__(self):
        self._tools: dict[str, dict] = {}

    def register(self, name, params_model, handler, *, timeout=5.0,
                 retryable=True, fallback=None):
        self._tools[name] = {"params_model": params_model, "handler": handler,
                             "timeout": timeout, "retryable": retryable,
                             "fallback": fallback}

    async def execute(self, name, raw_args, ctx=None) -> str:
        """统一入口：校验 -> 权限 -> 超时+重试 -> 降级 -> 审计。
        返回给模型的 JSON 字符串（会成为 ToolMessage 的内容）。"""
        ctx = ctx or {}
        start = time.perf_counter()
        audit = {"tool_name": name, "trace_id": ctx.get("trace_id"),
                 "conversation_id": ctx.get("conversation_id"), "caller": ctx.get("caller")}
        status, error_code, retries = "ok", None, 0
        try:
            tool = self._tools.get(name)
            if tool is None:
                raise NonRetryableError(f"工具 {name} 不存在")
            try:  # 1) 参数校验
                params = tool["params_model"].model_validate(raw_args)
            except ValidationError as exc:
                errors = [{"field": ".".join(map(str, e["loc"])), "message": e["msg"]}
                          for e in exc.errors()]
                raise NonRetryableError(json.dumps(
                    {"error": "validation_error", "errors": errors,
                     "hint": "修正参数后重试"}, ensure_ascii=False)) from exc
            if ctx.get("user_role") == "guest" and name == "query_order":  # 2) 权限(简提)
                raise NonRetryableError(json.dumps(
                    {"error": "permission_denied", "hint": "访客无权查询订单"},
                    ensure_ascii=False))

            async def call_once():
                return await tool["handler"](params)

            try:  # 3) 超时 + 重试
                if tool["retryable"]:
                    try:
                        async with asyncio.timeout(tool["timeout"]):
                            result = await retry_async(call_once)
                    except TimeoutError:
                        raise RetryableError("tool timeout") from None
                else:
                    async with asyncio.timeout(tool["timeout"]):
                        result = await tool["handler"](params)
            except RetryableError:
                retries += 1
                if tool["fallback"]:  # 4) 降级
                    result = await tool["fallback"](params)
                    result = {**result, "note": "主路径失败已降级，结果可能非实时"}
                    status = "degraded"
                else:
                    status, error_code = "error", ToolErrorCode.RETRY_EXHAUSTED.value
                    result = {"error": "retry_exhausted", "message": "服务暂时不可用，请稍后重试"}
            return json.dumps(result, ensure_ascii=False)

        except NonRetryableError as exc:
            status, error_code = "error", ToolErrorCode.BUSINESS_REJECTED.value
            return str(exc)  # 参数错误信息本身已是 JSON
        except Exception:  # 5) 兜底：内部细节只进日志，绝不给模型
            audit_logger.exception("tool internal error: %s", name)
            status, error_code = "error", ToolErrorCode.UNKNOWN.value
            return json.dumps({"error": "unknown", "message": "工具内部错误，请稍后重试"},
                              ensure_ascii=False)
        finally:  # 6) 审计（脱敏简化为整包打码，生产用 mask_args）
            audit.update({"result_status": status, "error_code": error_code,
                          "latency_ms": round((time.perf_counter() - start) * 1000, 1),
                          "retries": retries, "args": {k: "***" for k in raw_args}})
            audit_logger.info(json.dumps(audit, ensure_ascii=False, default=str))


executor = ToolExecutor()  # 组装
executor.register("query_order", OrderQueryParams, query_order, timeout=5.0, retryable=True)
executor.register("query_stock", StockQueryParams, query_stock, timeout=3.0,
                  retryable=True, fallback=query_stock_fallback)


async def main():
    print(await executor.execute("query_order", {"user_id": -1}))      # 校验失败
    print(await executor.execute("query_order", {"user_id": 7}))       # 正常
    print(await executor.execute("query_stock", {"sku": "SKU-DOWN"}))  # 重试耗尽 -> 降级
    print(await executor.execute("no_such_tool", {}))                  # 工具不存在


if __name__ == "__main__":
    asyncio.run(main())
```

> **设计说明**：执行器采用**注册表模式**——新工具只需写「参数模型 + 业务函数」，调用一次 `register` 就接入，校验/超时/重试/降级/审计全部白拿，业务代码保持纯净；**统一返回 JSON 字符串**——无论成功失败，模型看到的都是同构结构（用 `error` 字段区分成败），解析逻辑单一；**审计集中在 `finally`**——无论走哪条路径都会落一条日志。注意 `execute` 是异步入口，多个工具并发调用时各自持有独立的 `ctx`，不要用模块级全局变量存请求上下文（用 `contextvars` 或显式传参）。

### 8.1 调用时序

模型发起 `query_stock("SKU-DOWN")` 的完整路径：模型生成 `tool_calls`（参数是 dict）→ Agent 框架把调用交给 `executor.execute(...)` → 执行器 `model_validate` 校验通过 → 权限检查通过 → 进入 `asyncio.timeout(3.0)` 包裹的执行 → 第一次调用抛 `RetryableError`，`retry_async` 退避重试 → 重试 3 次仍失败，异常冒泡，`fallback` 存在 → 走缓存降级，返回带 `cached` 标注的数据 → `finally` 中写一条 JSON Lines 审计日志（耗时、重试次数、脱敏参数）→ 执行器把 JSON 字符串作为 `ToolMessage` 内容返回，模型读到 `{"sku": ..., "stock": 12, "cached": true, ...}` 后继续回答用户，并如实说明数据可能有延迟。

### 8.2 接入 LangChain

第八节的 `ToolExecutor` 是**纯手写**的执行器：不依赖 LangChain，任何 Agent 框架都能用。本节给出两种接入 LangChain 的方式，重点是**方式二**——用 LangChain 自己的机制把同一套工程逻辑重写一遍，最后用一张对照表标记两种写法的名称区别。

#### 8.2.1 方式一：薄封装（把执行器包成工具）

最省事的方式：执行器逻辑一行不动，用 `StructuredTool.from_function` 包一层壳，让它成为 LangChain 认识的工具（以你锁定的依赖版本文档为准）：

```python
from langchain_core.tools import StructuredTool  # 1.x 命名空间


async def _query_stock(args: dict) -> str:
    return await executor.execute("query_stock", args)


query_stock_tool = StructuredTool.from_function(
    name="query_stock",
    description="按 SKU 查询库存（结果可能来自缓存）",
    coroutine=_query_stock,
    args_schema=StockQueryParams,
)
```

特点：**执行器是核心，LangChain 只是外壳**。校验/超时/重试/降级/审计全部还在 `ToolExecutor.execute()` 里，LangChain 只负责「把工具交给模型、把返回字符串变成 ToolMessage」。缺点：你的工程逻辑和 LangChain 生态（回调、追踪、原生错误处理）是两套东西，LangChain 的观测能力看不到执行器内部。

#### 8.2.2 方式二：LangChain 原生实现（BaseTool 子类）

把第八节执行器的六件事**用 LangChain 自己的机制重写**：校验交给 `args_schema`，错误转结构化交给 `handle_tool_error` / `handle_validation_error`，审计交给回调（`BaseCallbackHandler`），权限交给 `InjectedToolArg`（见 01 文档 4.5 节）；**超时、重试、降级 LangChain 没有原生机制，仍在 `_arun` 内实现**——这也说明自定义执行层为什么必要。

```python
import asyncio, json, logging, random, time
from typing import Annotated, Any, Callable, Type

from langchain.tools import BaseTool                # LangChain 1.x 命名空间
from langchain_core.callbacks import BaseCallbackHandler
from langchain_core.tools import InjectedToolArg
from pydantic import BaseModel, Field

# 沿用第八节已定义：RetryableError / NonRetryableError、
# OrderQueryParams / StockQueryParams、query_order / query_stock /
# query_stock_fallback / retry_async（本节不重复贴）

audit_logger = logging.getLogger("tool.audit")


class ToolRejectedError(Exception):
    """业务拒绝（权限不足等）：对应手写版的 NonRetryableError。"""
    code = "permission_denied"


class AuditCallbackHandler(BaseCallbackHandler):
    """LangChain 原生审计钩子：代替手写 finally 审计（对应第八节第 6 步）。"""

    def on_tool_start(self, serialized: dict, input_str: str, *,
                      run_id=None, parent_run_id=None, tags=None,
                      metadata=None, inputs=None, **kwargs) -> None:
        audit_logger.info(json.dumps({
            "event": "tool_start", "tool_name": serialized.get("name"),
            "trace_id": (metadata or {}).get("trace_id"),
            "args": {k: "***" for k in (inputs or {})},     # 脱敏：整包打码
        }, ensure_ascii=False, default=str))

    def on_tool_end(self, output: Any, *, run_id=None,
                    parent_run_id=None, **kwargs) -> None:
        audit_logger.info(json.dumps({
            "event": "tool_end", "result_status": "ok",
            "output_summary": str(output)[:200],
        }, ensure_ascii=False, default=str))

    def on_tool_error(self, error: BaseException, *, run_id=None,
                      parent_run_id=None, **kwargs) -> None:
        audit_logger.info(json.dumps({
            "event": "tool_error", "error_type": type(error).__name__,
        }, ensure_ascii=False, default=str))


def _error_to_json(exc: BaseException) -> str:
    """LangChain 错误处理器：异常 -> 结构化 JSON（对应第八节第 4/5 步）。"""
    code = getattr(exc, "code", None) or "tool_error"
    return json.dumps({"error": code, "message": str(exc)}, ensure_ascii=False)


class EngineeringTool(BaseTool):
    """LangChain 版工程化工具：六件事用 LangChain 机制实现。"""

    # —— LangChain 契约：模型侧看到的就是这三个字段 ——
    name: str
    description: str
    args_schema: Type[BaseModel]                    # 对应手写版 params_model

    # —— 自定义配置（类似 register() 的参数）——
    handler: Callable                               # 对应手写版 handler（业务函数）
    timeout: float = 5.0                            # 对应手写版 timeout
    retryable: bool = True                          # 对应手写版 retryable
    fallback: Callable | None = None                # 对应手写版 fallback
    max_retries: int = 3

    # —— LangChain 原生错误处理：工具内抛出的异常自动转成工具返回值 ——
    handle_tool_error: bool | str | Callable[[BaseException], str] = _error_to_json
    handle_validation_error: bool | str | Callable[[BaseException], str] = _error_to_json

    async def _arun(self, user_role: Annotated[str, InjectedToolArg], **kwargs) -> str:
        """执行路径（async）：权限 + 超时 + 重试 + 降级。
        参数校验已由 args_schema 完成，失败自动走 handle_validation_error。"""
        # 权限检查（对应第八节第 2 步）：user_role 由应用注入，模型 schema 里没有
        if user_role == "guest" and self.name == "query_order":
            raise ToolRejectedError("访客无权查询订单")   # 会被 handle_tool_error 转成 JSON

        async def call_once():
            params = self.args_schema.model_validate(kwargs)   # 与手写版 model_validate 一致
            return await self.handler(params)

        try:                                        # 对应第八节第 3 步：超时 + 重试
            if self.retryable:
                try:
                    async with asyncio.timeout(self.timeout):
                        result = await retry_async(call_once, max_retries=self.max_retries)
                except TimeoutError:
                    raise RetryableError("tool timeout") from None
            else:
                async with asyncio.timeout(self.timeout):
                    result = await call_once()
        except RetryableError:                      # 对应第八节第 4 步：降级
            if self.fallback:
                params = self.args_schema.model_validate(kwargs)
                result = await self.fallback(params)
                return json.dumps({**result, "note": "主路径失败已降级，结果可能非实时"},
                                  ensure_ascii=False)
            raise                                   # 无降级 -> 交给 handle_tool_error
        return json.dumps(result, ensure_ascii=False)
```

组装与使用（对应第八节「`executor = ToolExecutor(); executor.register(...)`」）：

```python
tools = [
    EngineeringTool(
        name="query_order", description="查询订单状态",
        args_schema=OrderQueryParams,
        handler=query_order, timeout=5.0, retryable=True,
    ),
    EngineeringTool(
        name="query_stock", description="按 SKU 查询库存（可能返回缓存）",
        args_schema=StockQueryParams,
        handler=query_stock, timeout=3.0, retryable=True,
        fallback=query_stock_fallback,
    ),
]

# 交给模型：bind_tools，或 LangGraph 的 ToolNode / create_react_agent
llm_with_tools = llm.bind_tools(tools)

# 调用时挂上审计回调与追踪上下文（LangGraph 里通过同一个 config 传入）：
result = await llm_with_tools.ainvoke(
    "SKU-DOWN 还有库存吗？",
    config={"callbacks": [AuditCallbackHandler(audit_logger)],
            "metadata": {"trace_id": "trace-123", "conversation_id": "conv-1"}},
)
```

> 说明：`InjectedToolArg` 参数（`user_role`）在执行时由应用注入——可以来自 `ainvoke` 的 `config`、执行层的会话上下文，或 LangGraph 的图状态（详见 01 文档 4.5 节）。模型看到的 schema 里只有 `args_schema` 定义的业务参数，看不到 `user_role`。若你锁定的版本要求在 `args_schema` 模型内部声明注入字段（而不是 `_arun` 签名），以该版本文档为准。

#### 8.2.3 两种写法的名称对照（标记区别）

| 手写 ToolExecutor（第八节） | LangChain 原生（本节方式二） | 说明 |
| --- | --- | --- |
| `ToolExecutor` 类 | `EngineeringTool(BaseTool)` | 手写版是普通类；LangChain 版继承 `BaseTool`，成为生态一员 |
| `register(name, params_model, handler, ...)` | 类字段 `name` / `args_schema` / `handler` | 「注册」变成「声明一个工具实例」，列表即注册表 |
| `params_model` | `args_schema` | 都是 Pydantic 模型；LangChain 用它自动校验并生成模型可见的 schema |
| `handler(params)` | `_arun(**kwargs)` | 都是业务执行函数；LangChain 约定方法名 `_run` / `_arun` |
| `execute(name, raw_args, ctx)` | `tool.ainvoke(args, config)` | 统一入口变成 LangChain 标准调用 |
| `model_validate` + 手写错误列表 | `args_schema` + `handle_validation_error` | 校验失败不再手写分支，LangChain 自动转结构化结果 |
| 手写 `except NonRetryableError` 返回 JSON | `handle_tool_error` | 工具内抛异常即可，LangChain 统一收口转换 |
| `finally` 里手写审计 | `BaseCallbackHandler`（on_tool_start / end / error） | LangChain 原生观测钩子，还能接 LangSmith / Langfuse |
| `ctx` 里传 caller / user_role | `InjectedToolArg` + `config` / `metadata` | 身份不进模型 schema，由执行环境注入（01 文档 4.5） |
| 超时 / 重试 / 降级（手写） | 仍在 `_arun` 内手写 | **LangChain 没有原生机制**，必须自己实现——执行层的价值所在 |

两种方式怎么选：**已有手写执行器想快速接入**选方式一；**新项目、希望融入 LangChain 生态**（回调追踪、直接进 `ToolNode` / `create_react_agent`，阶段 3 项目推荐）选方式二。

关键点：LangChain 工具返回的字符串会成为 `ToolMessage` 的内容，所以执行器返回结构化 JSON 字符串（而非散文），模型才容易解析并继续；`error` 字段 + 错误码标记让模型识别「这次调用失败了，可以换方式重试或如实告知用户」。

给执行器写测试的三个要点：**mock 下游**（用 `unittest.mock` 或 httpx 的 MockTransport，不要真发请求）；**固定随机种子**（`random.seed(...)`，否则退避抖动让测试不稳定）；**断言审计**（执行后用 `caplog` 或临时文件验证审计行存在且字段正确）。工程化的价值一半体现在测试好写——工具逻辑与工程逻辑分层后，每一层都能独立验证。

## 学习自检与练习

1. **给工具加校验**：为「发送短信」工具写参数模型——手机号（`1[3-9]\d{9}` 正则）、内容（1~200 字）、定时发送时间（可选，晚于当前时间）。用 `model_validate` 写 5 个合法/非法用例并打印错误。
2. **封装 retry**：把第四节的 `retry_async` 抄下来，分别用「抛 `RetryableError`」「抛 `NonRetryableError`」的模拟函数验证：可重试的会重试、不可重试的立即失败且不消耗重试次数。
3. **写审计日志函数**：实现 `mask_args`（手机号/密码打码）和 `write_audit_log`（JSON Lines 落盘），手动构造一条「失败 + 重试 2 次」的记录并验证日志内容。
4. **设计降级逻辑**：给「天气查询」工具设计三级降级：实时 API → 昨日缓存 → 静态文案「天气数据暂不可用」。说明每一级返回给模型的 JSON 如何标注数据新鲜度。
5. **综合练习**：把第八节 ToolExecutor 跑通，再新增「下单」工具——要求：不可重试、10 秒超时、无降级、失败返回业务错误码。回答：为什么下单工具不能自动重试？
6. **思考题**：工具返回内容会进入模型上下文，结合第七节说明为什么「工具内部堆栈」绝不能出现在 `ToolMessage` 里；若模型看到了堆栈，可能发生哪两类问题？
