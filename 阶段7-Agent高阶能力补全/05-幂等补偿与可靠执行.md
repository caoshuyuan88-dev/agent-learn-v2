# 幂等、补偿与可靠执行

## 一、为什么 Agent 更需要可靠执行

Agent 可能因为模型重试、网络超时、Worker 崩溃、Checkpoint 恢复或用户重复提交而再次执行同一个动作。读操作通常可以重试，写操作可能产生重复扣款、重复通知或重复变更。

## 二、幂等设计

幂等不是“请求只发送一次”，而是同一个业务操作重复执行不会产生额外副作用。

```text
业务请求
  -> 生成稳定 idempotency_key
  -> 幂等记录 / 唯一约束
  -> 已完成：返回原结果
  -> 未完成：执行并保存结果
```

幂等键应来自稳定业务身份，例如：

```text
idempotency_key = hash(tenant_id + workflow_id + step_name + business_id)
```

不要把随机 request ID 作为重试幂等键，否则每次重试都会被当成新操作。

## 三、工具级实现示例

```python
from dataclasses import dataclass


@dataclass(frozen=True)
class OperationResult:
    status: str
    value: str


class IdempotencyStore:
    def __init__(self) -> None:
        self._results: dict[str, OperationResult] = {}

    def get(self, key: str) -> OperationResult | None:
        return self._results.get(key)

    def save(self, key: str, result: OperationResult) -> None:
        self._results.setdefault(key, result)


def send_notification(
    *,
    idempotency_key: str,
    recipient: str,
    store: IdempotencyStore,
) -> OperationResult:
    previous = store.get(idempotency_key)
    if previous is not None:
        return previous

    # 真实实现：调用外部通知服务时，也要把同一个 key 传给服务端。
    result = OperationResult(status="sent", value=f"notification:{recipient}")
    store.save(idempotency_key, result)
    return result
```

生产实现需要数据库唯一索引或原子写入，不能依赖单进程内存字典。

## 四、补偿与 Saga

当一个长流程包含多个有副作用的步骤，后续步骤失败时，不能假设所有步骤都能回滚。Saga 用每个正向步骤对应的补偿动作处理部分成功：

```text
创建订单 -> 锁定库存 -> 扣款 -> 发通知
    |          |         |       |
取消订单 <- 释放库存 <- 退款 <- 撤回通知/标记失败
```

补偿动作也必须幂等，并且要记录：

- 原始步骤状态；
- 补偿状态；
- 补偿尝试次数；
- 最后错误；
- 是否需要人工介入。

补偿不等于数据库事务回滚。外部 API、消息、邮件和人工操作通常只能做业务补偿。

## 五、可靠执行边界

- Workflow 负责状态和步骤；
- Activity / Tool 负责外部副作用；
- Retry 负责临时故障；
- Idempotency 负责重复执行；
- Compensation 负责部分成功后的业务修复；
- Human-in-the-loop 负责无法自动修复的异常。

Temporal 官方明确建议 Activity 设计为幂等，因为 Activity 可能因 Worker 故障而重复执行；这个原则同样适用于 Agent 的写入 Tool。

## 六、状态模型

```python
from typing import Literal
from typing_extensions import TypedDict


class StepState(TypedDict):
    name: str
    status: Literal["pending", "completed", "failed", "compensating", "compensated"]
    idempotency_key: str
    error: str | None
```

不要只在日志里记录补偿状态，应把它放入可恢复的 Workflow State 或数据库中。

## 七、练习

1. 为研发效能 Agent 的“创建分支、创建 Issue、发送通知”设计幂等键。
2. 模拟 Worker 在写入成功后、返回结果前崩溃。
3. 增加重复执行测试，验证不会创建重复 Issue。
4. 模拟第二步失败，执行补偿并记录最终状态。
5. 对无法补偿的情况触发人工审批。
