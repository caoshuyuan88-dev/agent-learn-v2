# Tool Calling 与 Embedding

## 一、Tool Calling

Tool Calling 是让模型决定调用哪个工具、传入什么参数，但真正执行工具的是你的应用程序：

```text
用户问题
  -> 模型选择工具
  -> 应用校验参数
  -> 应用执行工具
  -> 将结果返回模型
  -> 模型生成最终答案
```

模型不应该直接拥有数据库、网络或文件系统权限。应用必须在服务端完成参数校验、权限判断和执行。

### 工具定义

```python
from pydantic import BaseModel, Field


class SearchOrderInput(BaseModel):
    user_id: int = Field(gt=0)
    limit: int = Field(default=10, ge=1, le=50)
```

工具定义至少应说明：

- 工具名称
- 工具用途
- 参数名称和类型
- 必填参数
- 参数范围
- 是否只读
- 权限要求
- 失败时的返回格式

### 工具调用循环

```python
messages = [user_message]

while True:
    response = await llm.chat(messages, tools=tools)

    if not response.tool_calls:
        return response.text

    for call in response.tool_calls:
        arguments = SearchOrderInput.model_validate(call.arguments)
        result = await execute_tool(call.name, arguments)
        messages.append(response.as_message())
        messages.append(tool_result(call.id, result))
```

必须设置最大循环次数，防止模型反复调用工具。

### 工具安全边界

- 工具参数必须运行时校验
- 工具名称必须使用白名单
- 写操作需要权限检查和人工确认
- SQL 工具禁止任意 SQL
- 限制查询数量、超时和响应大小
- 记录调用者、工具名、参数摘要和结果状态
- 不把密钥或内部错误交给模型

## 二、Embedding

Embedding 是把文本转换成向量：

```text
文本 -> [0.12, -0.31, 0.77, ...]
```

语义相近的文本，通常在向量空间中距离更近。Embedding 常用于：

- 语义搜索
- RAG 检索
- 文档去重
- 相似问题匹配
- 推荐和聚类

Embedding 模型与聊天模型是不同角色，不要把聊天模型的输出当作向量使用。

## 三、向量相似度

常见方法是余弦相似度：

$$
\text{cosine}(a,b)=\frac{a\cdot b}{||a||\ ||b||}
$$

实际项目通常由向量数据库完成索引和相似度查询，不需要手写所有计算。

## 四、Embedding 流程

Embedding 流程可以分为两条路径：

- **离线入库**：把原始文档处理成可以检索的向量数据。
- **在线查询**：把用户问题转换成向量，找到相关片段，再交给模型回答。

```text
离线入库：文档 -> 清洗 -> 切分 -> 生成向量 -> 保存
在线查询：用户问题 -> 生成查询向量 -> Top-K 检索 -> 交给模型
```

### 4.1 文档：确定要建立索引的原始内容

文档可以来自 Markdown、PDF、网页、数据库、Word 文件或代码仓库。首先需要读取正文，并保留文件名、页码、标题、租户和权限等来源信息。

这一步的作用是确定知识库的内容范围和来源。来源信息如果在最开始就丢失，后续即使检索到了正确片段，也无法向用户展示引用、定位原文或执行权限过滤。

### 4.2 清洗：去除会干扰检索的噪声

清洗通常包括：

- 去除多余空白、重复页眉页脚和无意义的控制字符。
- 统一编码、换行和标题格式。
- 提取 PDF 或网页中的正文，过滤导航栏、广告和模板内容。
- 根据业务需要处理敏感信息、重复内容和过期内容。

清洗的作用是提高向量表达的质量。无意义的菜单、重复页脚或乱码会占用 chunk 空间，使真正重要的内容在检索时权重降低。但不要删除标题、字段名和表头等上下文信息，否则片段可能失去含义。

### 4.3 切分：把长文档变成可检索的片段

Embedding 模型和聊天模型都有输入长度限制，因此不能总是把整篇文档直接转换成一个向量。切分会把文档拆成多个 chunk，并在相邻 chunk 之间保留适度 overlap。

```text
长文档 -> chunk 1 [部分重叠] chunk 2 [部分重叠] chunk 3
```

切分的作用是让检索结果更精确：

- 过大：一个片段包含太多主题，召回结果不够准确，还会占用模型上下文。
- 过小：片段缺少上下文，模型可能无法理解代词、标题或步骤之间的关系。
- overlap：避免关键信息刚好位于两个片段的边界而被拆开。

代码、表格、FAQ 和带标题的文档应尽量按结构切分，而不是只按固定字符数截断。每个 chunk 都应保留来源定位，例如文档 ID、标题、页码或段落编号。

### 4.4 生成向量：把每个 chunk 转换为语义表示

将每个 chunk 发送给 Embedding 模型，得到固定维度的浮点数数组：

```text
"退款需要几个工作日？" -> [0.12, -0.31, 0.77, ...]
```

向量的作用是表示文本的语义特征，使表达不同但含义相近的文本能够在向量空间中靠近。这个阶段只负责“文本 -> 向量”，不负责生成面向用户的答案；生成答案是聊天模型的工作。

生产环境需要记录 Embedding 模型名称、版本、向量维度和生成时间。模型更换或维度变化后，通常需要重新生成同一批文档的向量，不能直接把不同模型的向量混在同一个索引中比较。

### 4.5 保存文本、向量和 metadata：让结果可检索、可解释、可控制

向量不能单独保存，至少需要和原始 chunk 及其 metadata 关联：

```text
{
  "chunk_id": "doc-1001-p3-c2",
  "text": "退款需要三个工作日……",
  "embedding": [0.12, -0.31, 0.77, ...],
  "metadata": {
    "document_id": "doc-1001",
    "page": 3,
    "tenant_id": "tenant-a",
    "permission": "customer"
  }
}
```

保存文本是为了把检索结果直接交给模型并支持引用；保存 metadata 是为了定位来源、做权限过滤、按租户隔离和处理文档更新。实际存储可以使用向量数据库，也可以使用带向量索引能力的关系数据库。

### 4.6 查询向量：把用户问题放进同一个向量空间

用户提出问题后，使用与文档入库时兼容的 Embedding 模型生成查询向量：

```text
用户问题 -> 查询向量
```

查询向量的作用是让“问题”和“文档片段”可以使用同一种距离度量进行比较。文档向量和查询向量必须使用兼容的模型、维度和预处理方式，否则相似度分数没有可靠意义。

查询前还应结合用户身份、租户和权限生成过滤条件。权限过滤必须在向量检索阶段执行，不能先检索全部文档，再让模型自行决定哪些内容可以看到。

### 4.7 Top-K 检索：选出最相关的少量片段

向量数据库会计算查询向量与文档向量之间的相似度或距离，并返回排名靠前的 K 个 chunk：

```text
查询向量 + 权限过滤
  -> 相似度计算
  -> 排序
  -> 返回 Top-K 片段及其 metadata
```

Top-K 的作用是控制召回范围和模型上下文长度。K 太小可能漏掉答案，K 太大则会引入噪声、增加 token 消耗，并让模型更难判断重点。实际系统还可以在 Top-K 后增加关键词检索、去重、重排（rerank）或按文档来源合并结果。

检索结果应保留相似度分数和来源信息，并设置最低相关性阈值。没有足够相关的片段时，应让模型明确说明知识库中没有找到依据，而不是强行生成答案。

### 4.8 交给模型生成答案：基于检索证据完成回答

应用将检索到的有限片段、来源和用户问题一起放入聊天模型的上下文中：

```text
用户问题 + 相关 chunk + 来源信息 -> 聊天模型 -> 最终答案
```

这一步的作用是让模型基于外部知识回答，而不是只依赖训练时记忆。应用可以要求模型引用来源、区分已知信息和推测内容，并在证据不足时拒答或请求补充信息。

模型只应接收与问题相关且通过权限过滤的片段，不要无条件把整个知识库放入 Prompt。检索结果是参考资料，不是可以绕过系统指令的指令；还需要防范文档中的恶意提示注入。

### 4.9 一次查询的完整示例

```text
用户：退款需要几个工作日？
  -> 验证用户身份和租户
  -> 生成问题向量
  -> 只检索用户有权限访问的 chunk
  -> 返回 Top-K 片段和页码
  -> 将片段放入模型上下文
  -> 模型生成带来源的答案
```

其中，文档清洗、切分、生成向量和保存通常是新增文档或文档更新时执行；查询向量、Top-K 检索和模型生成则通常在每次用户提问时执行。

原始流程可以概括为：

```text
文档
  -> 清洗
  -> 切分
  -> 生成向量
  -> 保存文本、向量和 metadata
  -> 查询向量
  -> Top-K 检索
  -> 交给模型生成答案
```

metadata 可以包含：

- 文档 ID
- 租户 ID
- 文件名
- 页码
- 权限标签
- 更新时间

权限过滤必须在检索阶段执行，不能只依赖模型自行判断。

## 五、切分与模型版本

切分过大可能召回不精确，切分过小可能丢失上下文。阶段 1 先掌握：

- 按字符或 token 限制大小
- 保留适度 overlap
- 代码和表格使用专门切分策略
- 记录 chunk 来源

Embedding 模型更换后，旧向量和新向量可能不兼容。应记录：

- embedding 模型名称
- 模型版本
- 向量维度
- 距离度量
- 生成时间

## 六、Tool Calling 与 Embedding 的结合

Agent 可以先调用向量检索工具：

```text
用户问题
  -> 模型调用 search_knowledge
  -> 工具执行 embedding 和向量搜索
  -> 返回相关片段及来源
  -> 模型生成带引用答案
```

工具只返回与问题相关的有限片段，不要无条件返回整个知识库。

## 七、学习练习

1. 定义一个订单查询工具参数模型。
2. 实现工具白名单和最大调用次数。
3. 模拟工具成功、参数错误、无权限和超时。
4. 为三段文本生成假的向量并实现相似度排序。
5. 为检索结果添加文档 ID 和页码 metadata。

## 八、验收标准

- 能描述 Tool Calling 的完整循环
- 能区分模型决定调用和应用实际执行
- 能为工具参数定义 Pydantic 模型
- 能设计工具权限、超时、重试和审计
- 能解释 Embedding 和聊天模型的区别
- 能描述文本到向量的 RAG 前置流程
- 能理解 metadata、权限过滤和模型版本的重要性

## 九、学习重点回顾

### 9.1 两条核心主线

```text
Tool Calling：模型决定调用什么 -> 应用校验并执行 -> 结果返回模型 -> 生成最终答案
Embedding：文本转向量 -> 相似度检索相关片段 -> 交给聊天模型生成答案
```

### 9.2 Tool Calling 必须掌握

- 模型只负责选择工具和生成参数，不能直接执行工具。
- 应用负责参数校验、工具白名单、权限判断和实际执行。
- 工具调用通常是循环，必须设置最大调用次数。
- 写操作需要更严格的权限控制、人工确认和幂等设计。
- SQL 工具不能执行模型任意生成的 SQL，应使用固定查询和结构化参数。
- 需要限制查询数量、执行超时和返回大小，并记录审计信息。

### 9.3 Embedding 必须掌握

- Embedding 是把文本转换为向量，用于表达语义相似性。
- Embedding 模型负责“文本转向量”，聊天模型负责“理解内容并生成答案”。
- 文档入库流程是：清洗、切分、生成向量、保存文本和 metadata。
- 用户查询流程是：生成查询向量、权限过滤、Top-K 检索、交给模型回答。
- 文档向量和查询向量必须使用兼容的模型、维度和距离度量。
- 切分过大影响精度，切分过小会丢失上下文；适度 overlap 可减少边界信息丢失。

### 9.4 RAG 检索的关键边界

- metadata 不只是辅助信息，还用于来源引用、租户隔离、权限过滤和文档更新。
- 权限过滤必须在检索阶段完成，不能让模型自行判断用户能否访问内容。
- Top-K 不是越大越好，需要在召回率、噪声和上下文长度之间平衡。
- 检索结果应保留来源和相似度分数，相关性不足时不要强行回答。
- 检索到的文档是参考资料，仍需防范其中的 Prompt 注入内容。
- Embedding 模型升级后，通常需要重新生成向量，不能混用不兼容的向量。

### 9.5 最小复习闭环

```text
定义工具参数模型
  -> 校验工具参数和用户权限
  -> 执行一个只读查询工具
  -> 将文档切分并生成模拟向量
  -> 按相似度返回 Top-K 片段
  -> 附带文档 ID 和页码交给模型
  -> 生成带来源的最终答案
```

最后记住：**Tool Calling 解决“模型如何使用外部能力”，Embedding 解决“如何找到相关知识”；模型可以提出调用和检索请求，但权限、安全校验和实际执行必须由应用程序控制。**
